## 多 Agent 段如何让观众理解协作

以下时间约到秒，不能作为精确剪辑点。

| 约时间 | 原片画面 | 叙事作用 | Mochi 应用 |
|---|---|---|---|
| 21–24秒 | Agent集群标题、同一个研究需求和发送动作 | 先交代共同目标 | 使用真实主会话需求；不以角色头像墙直接开始 |
| 25–27秒 | 主Agent一句话说明将组队、同时搜集；创建助手状态 | 解释为什么要多人 | 从已有原始协作记录抽取真实分派，不能编造Mo说过的话 |
| 28–32秒 | 角色卡从少到多、镜头拉开，再转换为精简成员状态 | 先认人和职责，再看整体 | 保留实际deck-maker/plan-writer/data-analyst；只用三位子Agent，不复制虚假的人数或进度 |
| 33–39秒 | 成员状态条与各自工作窗口、图表、任务过程交错 | 并行不是“很多头像”，而是各自做具体事 | 原会话按讲述顺序放大，同时保留其他真实会话在外围；明确历史回放，不暗示本轮正在并发 |
| 40–44秒 | 多组状态聚合，部分变为完成，成果逐渐替代成员卡 | 把人员规模转化为交付价值 | 成员会话缩回同一工作空间，真实教案、PPT和表格依次接位；状态必须有记录支持 |
| 45–49秒 | 进入报告、图表与文件清单，回到产品会话 | 用可用成果收束，而非再讲术语 | 进入真实课件翻页，再接课堂投递；不重复完整的聊天入口 |

## 对本片的决定

用户明确：群聊式表达仅用于影片，软件保持真实界面。采用“主会话发起 → 成员轮流成为画面焦点 → 工作并列 → 成果归队”的对话节奏；不仿造不存在的群聊页面，不给成员添加虚构聊天气泡。

K2.6用于学习“追加需求后继续工作”与网站/后端闭环；K2.5用于多Agent叙事；K3用于对象连续、空间交接与成果运动。三条片子各取适合的部分，不能混称同一条。

当前事实：已有24秒团队段包含真实成员切换、教案/课件历史与四款Mo配色；尚未证明完整发起→并行→汇总录屏。新的编舞不得把这个缺口隐藏成实时成功。叮咚与小信箱另外用原生组件和已存演示记录制作，作为学生协作段的补充。

此研究不代表新长片已渲染或全部功能验收。

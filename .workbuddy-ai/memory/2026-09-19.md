# 2026-09-19 工作日志

## 调研：Mochi 如何接入上游 DSH 的 Computer Use

**产出**：`artifacts/mochi-computer-use-upstream-adoption.md`（只读调研，未改生产文件）

### 核心结论
上游 0.1.6 把 Computer Use 做成了「MCP 包装 + 能力组独占注册」形态，**Mochi 不需要升内核、也不需要自研插件**：
只要在现有 0.1.3 内核上加**一个 MCP 挂载行**指向已安装的 `cua-driver` 可执行文件，模型就能拿到整套桌面操作工具（含截图看图）。

### 取证要点（一手证据）
- Mochi 内核 `0.1.3-alpha.1` 是 vendored 的 231 个 tgz（`vendor/alpha-family/`）；该版本**不在 npm 上**（npm 只有 `0.1.3-alpha.2`）
- 上游 npm：`latest` = `0.1.5-rc.2`，`alpha` = **`0.1.6-alpha.2`**（09-17）。Computer Use 首现于 `0.1.6-alpha.1`（09-15）。**第三方文章只讲到 alpha.1，已过时**
- 上游结构：`packages/computer-use/computer-use`（能力组，`ctx.computerUse` 独占注册）+ provider 在 `packages/experimental/`：`computer-use-cua-driver-mcp`（外部可执行 + MCP）与 `computer-use-cua-driver-native`（进程内 `@trycua/cua-driver@0.28.0`）
- 这些包**已上 npm**，但**不在** `@deepseek-ai/dsh@0.1.6-alpha.2` 的 77 项 dependencies 里 ⇒ 必须由 profile 显式挂载
- **关键**：0.1.3 的 `dsh-mcp-client` 已完整具备「外部 MCP 工具注册成 `mcp__<server>__<tool>`」+「MCP image 内容块 → attachment → 模型可见 image」（`src/tools.ts:355-358` `containsImage`/`prepareImageProjection`）
- `@deepseek-ai/dsh-mcp-client` 已是 `apps/desktop/package.json:91` 依赖；**但 base bundle 的 `cordis.patch.yml` 里没有任何 mcp 挂载行** ⇒ 缺口就是这一行
- 附件服务已挂（`packages/bundle/base/cordis.patch.yml:118-119` attachment-local）；mimo 两模型已声明 `inputModalities: ["text","image"]`
- **命名守卫零改动**：MCP 工具名 `mcp__x__y` 满足 `^[a-zA-Z0-9_-]+$`，且点号扫描只针对 `jxl.|mochi.|message.`
- **`mochi-modes` 天然上锁**：对话界面 restrict 只 allow `mochi_request_work_mode` ⇒ computer-use 工具默认不可见、不占 token

### 选型分水岭
- `cua-driver-mcp` 路线：**桌面权限由 cua-driver 自己持有**，理论可绕开「Mochi 未签名 → TCC 授权不持久」
- `cua-driver-native` 路线：**要求 Mochi.app 自己拿权限**，直接撞签名阻塞；且原生崩溃会杀掉宿主进程

### 签名现状（本次独立复现）
`build.mac` = `{identity: null, hardenedRuntime: false, gatekeeperAssess: false}`；产物实测 `Signature=adhoc`、`TeamIdentifier=not set`、`Info.plist=not bound`、无 `NSAppleEventsUsageDescription`。⇒ 本机 Demo 可用，发布给老师不可靠。

### 独立事实终审结果（一路独立 Agent，只读取证）
8 条核心论断 **7 条成立、1 条被证伪**：

- ❌ **被证伪（往好的方向）**：我初稿推断「`dsh-mcp-client` 不在 `PLUGIN_RUNTIME_MODULES` ⇒ 打包后 MCP row 可能解析不到」。**错**。实测打包产物 `Resources/app.asar.unpacked/node_modules/@deepseek-ai/dsh-mcp-client` 存在（该目录共 **231** 包，`dsh-base` 同在）。`PLUGIN_RUNTIME_MODULES` 只是**暂存 Mochi 插件**的 ESM import 闭包（脚本 `:218-221` 注释 + `:752-758` 拷到 `mochi/node_modules`），与内核 row 解析无关。**⇒ 路径 A 打包侧零改动，T2 已关闭**
- ✅ 补充事实 1：图片准入是**三条同时满足**——`ctx.get("attachments")` 已挂载 + provider/model/llm 路由可解析 + `resolveModelInfo().inputModalities` 含 `"image"`；任一不满足**不报错**，而是把图片降级为文本占位 `[image unavailable: <mime>; <reason>; raw image data remains available to programmatic callers]`。位置：`mcp-client/lib/index.js:317-334, 336-338, 357-370`
  - ⚠️ 这意味着**验收必须用「模型能否描述图内容」判定，不能看工具是否返回成功**
- ✅ 补充事实 2：工具名有 **64 字符总预算**，超长/撞名用 SHA-256 前 12 位十六进制去重后缀（`publicToolName()`）
- ✅ 补充事实 3：provider 的 npm 名带 `experimental-` 前缀，**与仓库目录名不一致**（按目录名查 registry 会 Not found）
- ✅ 补充事实 4：`packages/experimental/` 里还有 `browser-use-runtime`
- ✅ 补充事实 5：上游 git tag `dsh-v0.1.3-alpha.1` **存在**（tags API 可查），只是从未发 npm ⇒ 印证 Mochi 从源码 tag 构建后自行 vendored
- 📌 文档不一致：`vendor/alpha-family/SOURCE.md` 自称 "230-package closure"，实际 **231** 个 tgz
- 📌 全仓扫描：`computer-use` / `browser-use` 在 `apps/desktop` 的 resources/scripts/package.json 及 `docs/` 中**零命中** ⇒ Mochi 侧完全无接入痕迹
- 另：`Info.plist` 的 `CFBundleIdentifier` = `cn.jiaxinglian.mochi`，但 `codesign Identifier` = `Electron`（主可执行 linker-signed）

## 一条主线

教室端是给学生使用的共享管家，教师端是给老师使用的备课与班务管家。两端都直接给 Mochi 发消息；Mochi 从自然语言中提取必要字段，缺信息时在对话里追问，调用受限工具前由真实用户核对确认卡。LAN 面板只显示设备、发现、消息和回执状态，首次身份配置、短码配对、预约、回复、通知与叫人不再有独立业务输入表单。学生提交的问题不能因为 LAN 已投递就标成“老师同意”；教师发出的喊人或听写结果也不能因为教室设备收到就标成“学生已看到”。两端 UI 都应显示同一条已签名消息的真实阶段，不能维护第二份猜测状态。

**已确认的部署条件：** 教室电脑运行 Windows。**暂缓事项（用户 2026-09-24 明确要求先不做）：** 依据每节课自动打开教师偏爱的 APP；它要与尚未明确的课表来源及定时任务一起设计。当前没有自动启动实现，不把普通提醒写成启动成功。学生发消息不能借此获得任意 APP、命令、路径或网址执行权。两端背景可以各自通过对话切换并保存偏好。

**配对批准身份待定：** 教室电脑由学生共用。现有 LAN 角色锁定、同校校验、签名设备指纹和双端确认只验证设备与请求；聊天“允许一次”和 LAN 面板“核对后接受”都没有验证操作者是老师或管理员。代码中已有校园登录及会话绑定，但它尚未接入这两条配对接受路径。若规定仅教职工批准，最小可复用方向是验证校方账号角色并同时封住聊天工具和 LAN 面板；这依赖学校账号体系及登录状态，断网时须决定是否拒绝新配对。共享 Windows 账号名、六位匹配码和单次点击都不足以证明成人身份。当前等待批准者政策确认，不能将本机确认测试表述成成人授权测试。

**语音方案：** 用户选择主安装包不内置语音模型。教室端后台自动下载并校验 sherpa-onnx Windows CLI 与 Kokoro 中文模型，两份压缩包合计约 164.4 MB；安装好后在本机离线合成，不用供应商 API Key，也不把叫号内容发到语音服务。下载期间用 Windows 已安装的中文语音。学校若不能访问 GitHub，管理员可按[固定哈希归档导入说明](Windows-voice-pack-offline.md)将两份资源放到教室用户目录；本地归档同样先校验再安装。前两次原生 CI 曾在 BZip2 列表阶段超时；[run 36030805114](https://github.com/linkimi2026-cmd/jyl-campus-health/actions/runs/36030805114) 使用随 Windows 包提供的 7za 成功解包并完成实际 Windows Kokoro 合成，18,044 B WAV 检查通过。该 CI 证明固定资源与 Windows 合成路径可运行，不代表目标学校电脑的安装与播放体验已验收。扬声器音质、声量仍须现场试听。弹窗与常驻板始终是准确信息源，设备尝试播报不自动替代人工已看到回执。

- **已确认：** 多位教师已配对时，教室预约需要明确选定接收教师，确认卡列出目标身份和指纹；预约讲题必须填写希望的时间。聊天里的六位码工具会重查本机已发现的同校教室，最多等待 30 秒；当前候选均已核查后可提前结束，发现关闭时可能立即返回。若到时仍有候选未核查，没有指定设备 ID 时不会把一个部分匹配当作唯一目标；同一教师进程内相同短码的并发搜索会被拒绝，避免重复消耗限额。只对经过身份签名和 nonce 核验的明确错码回执做本进程负缓存，最长两分钟；候选暂不可达不缓存，并会在新发现或地址变化后有限重试。自动发现仅使用本机 UDP 广播/组播候选，不能凭短码跨越无路由的 VLAN；诊断会区分没有发现候选、候选不可达和短码被拒绝。对话仍可补充教室 IPv4 和端口进行手动探测/配对。教师发件箱现显示签名名册中的逐人处置和投递/人工回执，桌宠发送记录行可定位到该详情；这一轮尚未用学校真实有线双机验收。
- **已确认：** 本轮 LAN 本机双进程测试覆盖多 IPv4 网卡定向广播地址、短码过期/限频/签名挑战/双端确认，以及预约回复绑定原请求、精确重试与第二份冲突回复拒绝。配对接受的 HTTP 回执丢失后，教师服务重启，教室用同一请求 ID 重试仍能双端配对；并发使用同一个短码只有一条请求入队。学生预约首次提交固定消息 ID，回执丢失后重复确认在教师收件箱仍只有一条。教师可人工标记看过预约；教室端“我的预约进度”展示送达、教师查看、确认/改期与本机人工查看。已收到匹配签名查看回执的回复不再提示重试。无可用广播/组播时显示发现降级，保留手动地址。投递 ACK 与人工“已看到”分开。
- **已确认：** 发现服务现对每条实际 IPv4 网卡路由发送广播并加入对应组播，网卡拔插时同步成员和发送 socket；单路失败时保留另一条路径，全部失效后定时重建，恢复后回到 `ACTIVE`。故障注入覆盖同网段双接口、广播单路失败与恢复、端口先占用后释放、网卡拔插。教室页面显示本机非回环网卡 IP 和监听端口，供教师尝试手动连接；隔离 DSH 页面实测 `en0` 地址可见。误拉黑设备可在确认弹窗解除禁止标志，真实页面验证旧配对不会因此恢复。上述证据仅限本机网络与模拟多网卡，未证明校园有线双机可达。
- **已确认：** 两个隔离的实际 DSH 页面完成了人工配对和预约闭环：教师用手动 `127.0.0.1` 地址及教室屏短码找到设备，双方核对学校、班级和指纹后确认；教室提交预约，教师待办出现并签名标记已看，教师确认时间后，教室显示决定，教室再人工确认已看到回复。受控路由强制双方身份后，另用新临时数据根重跑教室预约→教师确认→教室人工已看到→教师收到回执，均由真实页面/签名状态证实。再用临时浏览器响应模拟同 endpoint 换指纹：确认卡展示新指纹，最终发送被服务以 HTTP 409 `LAN_APPROVAL_STALE` 拒绝，教室发件数未增加，拒发提示在后台刷新后仍可见。键盘 Enter 打开弹窗后焦点移到关闭按钮，Tab 环绕、关闭后焦点归还原按钮。追加页面检查确认教师发件箱逐人详情可见；用合成的第二名教师验证教室必须选定目标、核对指纹后才能进入发送确认。合成第二教师未做真实签名发送。该 fixture 特意关闭 UDP 发现，故页面实测的是手动地址、短码、目标选择和已签名预约闭环；自动发现另由本机协议测试覆盖。
- **已确认（自然语言预约双实例的初版）：** `test:chat-appointment-live-ui` 的初版同时运行隔离教师与教室 Electron/DSH，由本机脚本化 SSE 模型驱动真实工具调用和“允许一次”审批。教室提交的预约获得签名投递确认；教师读取原请求、按原消息 ID 确认原时间；教室收到签名决定且面板刷新后显示原时间。当时配对状态由真实 LAN 服务预置在测试目录，因此只证明预约部分的工具、审批、签名和界面接线；后续测试已补齐聊天配对，见下一条。
- **已确认（双端聊天配对续接预约）：** 上述测试现从双方均未配对的身份启动，不再预置已配对状态。教师聊天发起配对并点一次审批，教室聊天先用 `mochi_lan_status` 读取实际待确认请求，再用其请求 ID 调 `mochi_lan_decide_pairing` 并点一次审批；测试核对双方真实 Electron LAN 服务中的对端 ID 与指纹一致，然后在同一聊天会话续发学生预约、教师原时间确认和签名结果。测试中的模型响应由确定性本机 SSE 夹具产生，**没有验证真实模型理解自然语言**；审批按钮也只证明本机使用者点击，不能证明点击者为老师或管理员。学校有线双机、目标账号权限和实际 Key 仍须现场验证。

## 界面与动效

教师常驻条收成一个可识别的 Mochi 小角色，默认只显示待办数；点击展开原位置的待办卡。卡片先显示学生、问题与可约时间，点击卡片定位原预约，再在完整页面确认或改期，减少读完整段文字才能判断的时间。窗口不抢焦点，关闭回到同一位置；按压即时反馈，展开和收回可被反向点击打断。玻璃材质只用于浮层，正文保持足够对比度。支持键盘、`prefers-reduced-motion`、`prefers-reduced-transparency` 与高对比度。

视觉来源已复核：相邻 `联动计划` 仓库 HEAD `cd17ff8337e20ed02f632fbf97625e0b668cc3cf` 的 `OrbCompanion.tsx`、`OrbCompanion.css` 与 `ExpressiveOrb.tsx/.css` 绘制表情球和小电脑。Mochi `jxl-brand` 复用该 SVG 组件，动效 CSS 由本仓维护无障碍覆盖；桌面 renderer 是平台适配副本，独立 rail 窗口为自包含的缩小 SVG/CSS 版本。当前还找到 `参赛PPT/Mochi四分钟答辩/assets/Mo-品牌原画.png` 与 `docs/assets/loose/Codex 图像 2026年9月8日 22_52_33.png`，两张都画圆球加电脑。全树检查 737 张 PNG/WebP/GIF，未找到独立“小螃蟹”素材；文件元数据未证明作者或授权。[Codex Pet 的 Claude Crab 页面](https://www.codex-pet.com/pets/claude-crab)虽有图集，公开清单没有该图的再分发许可，不能据此装进 Mochi。与 Clawd on Desk 的关系目前可证的是行为灵感，未将其代码或保留权利的美术作为 Mochi 素材。联动计划原注释误写其为 MIT，不能据此扩展授权判断。

教室板是给全班看的，维持大字号和明确的处置状态；它不缩成教师桌宠。教师端通知是待处理工作，不是每 3 秒轮询就重复弹窗。新预约一次提醒，后续静默更新；办公室喊人需有地点，必要时给时间；听写名册按批弹一次、按人显示。人数超过常驻板 50 行容量时，末行明确提示剩余结果并提供完整名册入口，不把被隐藏的学生当作已展示。

本轮桌宠经真实 Electron 画面检查：折叠态显示 Mochi 焦糖球、小电脑和需处理数，展开态两条示例预约完整可见；64 人教室板顶部与末尾溢出入口也已截图核对并点击验证。展开标题栏的收起按钮现保持在折叠宠物原来的屏幕点击位置，有角标和无角标都用真实坐标点击验证；快速反向点击不改变右缘。`prefers-reduced-motion` 用 Chromium 媒体模拟证实停止球、眼、电脑和字符动画，降低透明度和高对比度有对应样式，窗口边界动画可反向打断。待办区分“待查看”“已看待回复”“回复投递中/未知”“教室已收件/已看到”，保留学生期望时间和教师决定；点击定位原预约，不自行把“教师已看”改写成“已确认”。身份或配对变化后的旧预约、旧发件标为历史，不占待办数。教师喊人/听写的出站记录与真实投递状态可定位到 LAN 面板中的逐人详情；未送出或结果不明进入角标，但不冒充新的学生预约弹窗。LAN 弹窗在键盘打开时获取焦点，Tab 限于弹窗内，Esc 关闭后焦点返回原按钮。

收尾回归还验证：60 条教师待办被 50 行展示上限裁剪时，角标视觉保留 9+，辅助技术仍朗读真实 60 条；64 人教室名册虽只展示 50 行，角标与播报仍为 64。教师桌宠展开后网页重载，主进程会恢复页面的展开状态；随后第一次点击仍能正常收起。高对比媒体模拟显示实色面板和桌宠、无模糊。启动视觉生成物在真实 Chromium 的六种表情态下，系统减弱动效与显式静止态均停掉动画和过渡，普通 typing 保留动效。真实 Windows 桌面合成效果尚待 Windows 目标机核查。

## 验收顺序

1. 角色运行：教室本机能打开原生模型密钥卡并保存到教室 home；教师密钥与教室密钥隔离。错误状态区分“未填”“已保存但未测”“真实调用拒绝”。打开模型页静置半分钟，确认请求不会持续循环；分别在新会话和已有会话切换模型后验证实际调用。
2. LAN：有线网卡、无线网卡、无 UDP 发现、地址漂移、错误学校/班级/指纹；短码过期、错误、碰撞与限频。双端人工确认后发消息，再重启自动恢复。现场先确认两端 IP 是否互访及跨 VLAN 发现策略；仅有短码不足以跨网段定位。
3. 预约：提交 → 教师待办 → 确认或改期 → 原教室显示结果；离线与重试不重复决定。办公室通知和听写不过关分别验证具体内容与人工已看到回执。
4. rail：点击展开/收回、反向操作、键盘、降低动效/透明度、不同分辨率；真实通知内容在首屏可见。用超过 50 人的实际听写名册检查溢出行、完整名单定位及聚合提醒。
5. PPT：生成真实可编辑文件，检查来源、全册节奏和密集页，渲染后看图；只改有证据缺陷页。新能力须回读 PPTX 与 PDF，并与旧版做同输入对照。
6. 语音：Windows 教室机首次联网下载校验语音包期间，核对已安装中文系统语音的临时回退；下载完成后离线喊一名学生，实听音色、音量和教室扬声器覆盖。让学生确认弹窗/公示板内容，核对“设备尝试播报”不会冒充人工已看到；学校网络无法下载时按固定哈希归档离线导入。
